# Rule Construction — Architectural Blueprint\n\n## Purpose\n\nThis document records the project-specific architectural rules established for constructing and composing Fail-Closed rules. It is a project contract/reference document, not an implementation specification by itself.\n\n## Knowledge Precedence\n\n1. Internal project knowledge and approved project contracts are the primary source.\n2. External references and current best practices are fallback evidence only when internal knowledge is missing, insufficient, conflicting, or requires current verification.\n3. External information must be reviewed as a Delta/Conflict Review before changing an approved project contract or architecture.\n4. External evidence does not automatically authorize repository mutation.\n\n## Rule Construction Model\n\nRule Construction has three architectural layers:\n\n- Rule Atomicity — each rule has one bounded responsibility and its own semantic authority.\n- Composition Operators — rules are combined through explicit operators such as Sequential Gate and Logical Guard.\n- Execution Pipeline — the runtime order enforces the required evidence and authority boundaries.\n\nRules are intended to be orthogonal: one rule must not repair, reinterpret, or replace the semantic responsibility of another rule.\n\n## Integrity Matrix\n\nFor a Replace request, the required integrity pipeline is:\n\nI-01 Context Digest → I-02 Lineage → I-03 Transaction / Target Identity → I-04 Lifecycle Provenance → I-05 Authorization Context\n\n### I-01 — Context Digest\n\nProves that the Execution Context being evaluated is the expected immutable context.\n\nA digest mismatch is an Integrity Failure and must not be interpreted as NOT_COMMITTED, Unsupported, or authorization failure.\n\n### I-02 — Lineage\n\nProves causal consistency between source context, transition, and target context.\n\nExamples of violations include:\n- transition source does not match target parent;\n- target creator transition does not match the transition under review;\n- transition target does not match the target context identity.\n\n### I-03 — Transaction / Target Identity\n\nProves that the target/result belongs to the immutable transaction identity being evaluated.\n\nCurrent state alone cannot identify which concurrent transaction produced that state.\n\n### I-04 — Lifecycle Provenance\n\nProves that current lifecycle state is explainable by its immutable lifecycle event history, including state transition, state version, event continuity, and transition identity.\n\n### I-05 — Authorization Context\n\nProves that the operation remains authorized for the exact validated Execution Context, contract/version, policy/version, target context, and declared validity mode.\n\nAuthorization validity does not establish Context Integrity.\n\n## Ordering Rules\n\n### IM-ORDER-01 — Integrity Precedes Authority\n\nAuthorization Context MUST NOT be semantically evaluated for a mutation until all required upstream Integrity and Causal validation gates have passed.\n\nRationale: authorization is meaningful only relative to a context whose identity and causal integrity have already been established.\n\n### IM-ORDER-02 — Downstream Authority Cannot Repair Upstream Evidence Failure\n\nA successful authorization result MUST NOT override, repair, downgrade, or reinterpret an upstream Integrity Failure.\n\n### IM-ORDER-03 — Gate Failure Is Monotonic\n\nOnce a required Integrity gate fails, downstream gates MUST NOT restore the request to an executable semantic state.\n\n## Sequential Fail-Closed Composition\n\nThe Integrity Matrix uses the SEQUENTIAL_FAIL_CLOSED composition operator:\n\n- Gate N executes only when required Gate N-1 has passed.\n- A required failure stops downstream semantic evaluation.\n- Required failure results in BLOCK for the affected semantic operation.\n- No semantic mutation, result recovery, or blind retry is permitted from the failed path.\n- Failure evidence must remain available for diagnostics and causal analysis.\n\nStopping downstream evaluation does not mean discarding independently detected evidence from other validation sources.\n\n## Orthogonality\n\nEach Integrity layer has a distinct responsibility:\n\n| Layer | Responsibility |\n|---|---|\n| I-01 | Context Integrity |\n| I-02 | Causal Lineage |\n| I-03 | Transaction / Target Identity |\n| I-04 | Lifecycle Provenance |\n| I-05 | Authorization Context |\n\nNo layer may act as semantic authority for another layer.\n\nExamples:\n- I-01 does not authorize a transition.\n- I-05 does not repair a digest mismatch.\n- I-03 does not authorize a lifecycle transition.\n- I-04 does not create lifecycle state.\n- Integrity validation does not itself prove transaction commit.\n\n## Multiple Integrity Failures\n\nWhen several integrity layers fail in the same observation:\n- preserve the primary failure;\n- preserve secondary evidence;\n- do not allow the first sequential failure to erase independently detected causal evidence;\n- do not reinterpret one failure as another failure class;\n- preserve enough evidence for later Outcome Resolution and recovery/escalation.\n\nThis is the basis for the next Rule Composition review: I-06 Multiple Integrity Failures.\n\n## Integrity vs Outcome\n\nThe Integrity Matrix produces evidence about the trustworthiness of the records and context.\n\nIt does NOT by itself prove transaction outcome.\n\nOutcome Resolution must separately establish:\n- immutable transaction identity;\n- source identity;\n- target identity;\n- causal lineage;\n- lifecycle provenance;\n- authorization context;\n- actual transaction outcome.\n\nTherefore:\n\nIntegrity PASS != COMMITTED\n\nand:\n\nIntegrity Failure != NOT_COMMITTED\n\nA response-loss recovery must never create a new semantic mutation merely to reconstruct an old result.\n\n## Outcome Resolution Guard\n\nWhen a Replace response is lost:\n\nOUTCOME_UNKNOWN → identify immutable transition/idempotency identity → validate the causal evidence bundle → determine transaction outcome\n\nPossible results:\n- RESOLUTION_CONFIRMED_COMMITTED → recover the original result without mutation.\n- RESOLUTION_CONFIRMED_NOT_COMMITTED → enter retry eligibility and start a new transaction with fresh validation.\n- RESOLUTION_OUTCOME_UNKNOWN → no blind retry; continue approved recovery.\n- RESOLUTION_INTEGRITY_FAILURE → block recovery and escalate/recover under the applicable authority.\n\nCurrent Context State is evidence, not Transaction Identity.\n\n## Knowledge Boundary\n\nProject-specific architectural decisions recorded here are distinct from general engineering best practices.\n\nWhen external references are introduced:\n\nExternal Evidence → Delta/Conflict Review → Contract Decision → Architecture Update\n\nnot:\n\nExternal Evidence → Automatic Contract Change\n\n## Governance\n\nThis document records architectural knowledge and invariants. It does not by itself authorize implementation changes to protected runtime, Apple Adapter, DNS Runtime, CI, PRs, or other protected work.\n\nImplementation remains subject to:\n\nEvidence → Boundary → Contract → Implementation → Test → Runtime Evidence.\n
